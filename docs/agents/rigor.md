# Rigor

People navigate, plan and do research with what Open Waters publishes. A wrong answer that looks right does more harm than a missing one, because nobody knows to distrust it. A change isn't done until it's right, however long that takes. Every contributor, person or agent, works to these rules. The shared [review prompt](../../skills/openwaters-review/review-prompt.md) checks for workarounds, plausible defaults, and disagreements explained away, and, when a pull request exists, claims about every case that rest on a sample and deferred work that isn't blocked. The rest are the author's to keep.

- **Diagnose, then fix the cause.** When something fails or looks wrong (a test, a build, a tool, a dependency, a source's data), find out why before changing anything. Reproduce it, read the error and the code behind it, and name the cause. Then fix it where it starts, even when that's in another module, another repo in the org, or a shared script. Don't skip, retry, catch and ignore, special-case, pin around, loosen a check, or change a test's expectation to make the symptom go away. Handling an expected, documented condition, such as retrying a documented transient failure, ignoring an optional file that's missing, or a pin the repository's standards require, isn't a workaround. If the cause is outside our control (an upstream bug, an agency's broken file), fix what we can, report it upstream, and keep the workaround small, commented with the cause and a link to the report, and listed under the pull request's `## Known limitations`. If you can't find the cause, stop and say what you tried rather than shipping a guess. The same holds for prose: a disagreement with an independent reference (an agency's published values, another implementation, observations) is a failure still to diagnose. A report, doc, test expectation or pull request that explains one with a cause neither a test nor a cited primary source shows, or lists it as known or expected without one, is a workaround.
- **Check all of it, not a sample.** A spot check can find a problem but can't show there isn't one. A claim about every record, file, platform or source rests on a check of every one. Where only a sample was possible, say how many of how many, and the claim stays "checked n of N", never "all". When one case turns out wrong, check every other one that could be wrong the same way before calling it isolated.
- **Verify against reality, not code.** Passing tests and code that looks right don't show the result is right. Run it and look at what it produced: the files, the app, the API response, the rendered chart. Before review, check a local run; once the change ships (on merge, deploy or release), check what production produced, as a step under `## After merge` in the pull request's description.
- **Research facts, don't guess them.** Standards, datums, units, API behavior and terms come from the primary source, cited. If a search, a page read or a probe would settle a question, do it rather than ask or assume. If you can't confirm a fact, write "not confirmed" and treat it as a blocker.
- **Policy decisions stand; precedent proves nothing.** A maintainer's decision on policy, such as a permission, a license or a source's terms, stands; don't reopen it in each change. Everything else earlier work did is not evidence that it's right, and "it was done this way before" is never the justification. When the evidence shows an earlier choice was wrong, raise it, fix it, and check whatever else made the same choice. A decision that is genuinely open goes to a maintainer, and a pull request opened with one still open is a draft.
- **Finish the whole job.** Work the task needs isn't a follow-up. Only work that is genuinely blocked goes under a pull request's `## Known limitations`, naming what's missing and why.
- **Review until no high or medium findings remain.** Verify every finding against the code or the data before fixing or dismissing it. When to run another round, and when to stop and hand open findings to a maintainer, is in the review skill's [Acting on findings](../../skills/openwaters-review/SKILL.md#acting-on-findings). Low findings it lets you leave unfixed are listed in the pull request's `Review` section, an exception to finishing the whole job.
- **Report what was done, as it was done.** Say what was checked, how and over what, and what wasn't. Never round "most" up to "all", or "should" up to "does".
- **Never fill an unknown with a plausible default.** A value you can't confirm is flagged, left out or refused, with the reason recorded, not published as if it were sound.
