Code review, read-only. Do not modify files.

Review this branch as a change to a running system, not as a diff. Most real defects are in how the change meets code it does not touch. A review that only reads the diff has failed.

Step 1. Map the system before judging anything. For every table, column, file, cache, config key, env var, API field, message, and shared function the change reads or writes, search the whole repository for every other writer and reader: live ingest, replay, archive and historical loaders, converters, backfills, migrations, scheduled jobs, clients, scripts, and docs. List each one with file:line. Do not skip this step.

Step 2. Check the change's assumptions against every writer and reader from step 1, and against all the data that can actually exist: every source and prefix, rows written by other paths, rows written by older code before a migration, nulls, defaults, duplicates, and out-of-order or late data.

Step 3. Check the upgrade from what is deployed today: existing schema and data, migrations run in place, caches and their max-age, old clients still running, and rollback to the previous release. Is the in-place upgrade tested, or only a fresh install? For any marker or state only the new build writes, walk new build, rollback, older build runs, roll forward: does the marker still describe the data the older build left?

Step 4. Check every claim against the code: comments, READMEs, docs, policy, API descriptions, the commit messages (git log), and the PR description if one exists (given at the end of this prompt). Treat each claim, and each test or validation result, as a hypothesis to attack. Ask what cases the tests and validation data leave out. Follow the claims the change leans on but does not contain: when changed text cites another doc section, policy, or mechanism, confirm that mechanism exists in code. For every license, privacy, or redistribution condition attached to new data, such as an opt-out, suppression, attribution, or a ban on re-identification, find the code that enforces it on that data's path, or report that nothing does.

Step 5. Read the repository's CONTRIBUTING.md, if it has one, and the files in the repository it links. Check the change against their conventions and the repository's other documented conventions, the checks its scripts and CI enforce, and every item in its `Review checks` section, if it has one. Those items are this project's known traps; treat each like a class in step 6.

Step 6. Check these classes. Each asks you to name a concrete input, caller, or interleaving. Check every clause of a class; one clause that does not apply does not excuse the rest.

- Inputs at the edges. For each value the change parses, encodes, compares, or accepts, name the input that breaks it. For code that splits or matches text into fields (a regex, a split on a separator, a tokenizer), feed three rows, each with one empty field (first, middle, last) and distinct values in the rest, so a shift shows which value moved and what the caller then reads from the wrong column; then a quoted field holding the separator, a quote, or a line break, a blank or trailing line, and CRLF endings. When parsed fields build a date, time, or index, or a parser reads a whole date from external text (a source's file, a form field, a note in a CSV), try out-of-range values (month 13, 31 November, `2019-02-31`), which date constructors and lenient parsers roll into the next unit without an error (JavaScript's `Date.parse("2019-02-31")` gives 3 March), and a fixed-layout file with a record missing or repeated (a line per day, a row per hour). The code must range-check each field, or format the parsed date back in the input's own layout and compare the parts (or use a strict parser for that layout), and reject the value on a mismatch, and must report a missing or repeated record instead of reading it as a gap; name the input that comes out as wrong or missing values instead. Also try duplicates; two items that tie on every key a sort or choice compares (does a final key such as the ID make the result the same on every run?); values that do not survive a round trip through encoding (paths from keys, URL or query encoding, serialization, a number that can be `Infinity` or `NaN`, such as a division by zero or a statistic of too few samples, saved as JSON, which has no way to write it: name what the writer emits, since JavaScript writes `null`, Python a bare `Infinity` that strict parsers reject, and Swift and Go fail the save, and what each reader then does with it); a second input shape the code newly accepts while tests and callers still assume the old one; and an empty, truncated, or unrecognized input to anything that deletes what its input no longer lists, which must stop the removal rather than log and report success. Prefer an existing parser in the repo or standard library over a new regex.
- Every other path to the same result. When the change sets a rule, value, field, flag, or parameter, find every other writer, route, caller, serializer, fallback, and doc that produces or states the same thing, including code the diff does not touch and callers the base added after the branch point. A refused input may pass through a later fallback, a second matching key, or a bulk or admin path. A response field may be missing from other status codes, redirects, partial answers, or another serializer (omitempty, nil versus empty). A status flag such as truncated or stale may be set by paths its doc does not name. A changed precision, unit, or limit may survive as the old number, a multiplier (`* 1000`), a format call, or prose ("three decimals"). A gate path list (a CI paths filter, a git diff -- gate) may miss root manifests, lockfiles, workflows, or container files. Name each path that skips the check, emits the old value, or omits the field. When the change adds or edits a value that has a source (a constant, a config key, or the doc section that defines it), name each literal in code, comments, or docs that copies it instead of referring to the source. Tests that pin the value by hand are not copies.
- Rules read literally. Does each filter, guard, precedence, or override enforce the exact rule its comment or doc states? Check both bounds; which side a conservative rule (fail closed, deny by default, round toward safe) keeps and which it drops; what unit a win applies to (a whole file, a record, only the overlapping items); and every mix of set and unset overrides, not only all or none, where one override collides with a value the code picks for another (two listeners on one port, two writers to one file). Rate a collision by its effect, not by how unlikely the mix seems. Name the input where following the wording drops what the rule exists to protect.
- Order and interleaving. Name the input or interleaving where something is decided on stale state: a gate or set computed before a later step (a deny-list, an override, a validation) drops some of its inputs; a fallback chain that ends when one candidate is found but fails a later stage (its fetch, decode, validation, or timeout) instead of moving on; a read-then-write on shared state (a lock, a lease, a marker, a row) that is not conditional on the version read (compare-and-swap, If-Match, a version column), including release and cleanup paths; state that must agree (a count and the list it counts, two maps written to one file) read under separate locks or transactions; a reset whose own work can end in the state that triggers it again.
- What the change leaves behind. Follow the change through later runs and through systems that ran the old code: hand-maintained references (config, overrides, allow-lists, fixtures) to ids another process regenerates, followed through each consumer on a run where the id is gone; services, scheduled jobs, files, env vars, secrets, storage, database objects, and feature flags that removed code leaves and the deploy does not clean up; and specs, plans, and docs that still describe what was removed. Name what crashes, misbehaves, or stays stale, and the check that should report it.
- Production conditions. Name the environment or size where the change fails though local checks pass: another runtime that loads the module (browser, edge worker, another platform version) where module-level code needs the filesystem, process, globals, native modules, or platform APIs, and whether any check actually starts it (a dry-run bundle does not); a memory, time, or size limit, where "unmeasured" is not an answer: give the commands and production-like synthetic input to measure peak memory and time for old and new code; every timeout on a long operation's path (client, driver, proxy, load balancer, server, job runner, supervisor); production paths that a mock or small data skips (pagination, batching, multipart, rate limits); a CI or deploy job where branch or dependency code (install scripts, builds, test runners, loaded config) runs beside a secret, unless build and publish sit in separate jobs that pass only built artifacts; and a touch or keyboard user who cannot reach required content shown only on hover, or a control nested inside a link.
- Tests that prove the claim. For each property the change claims (concurrency, a limit, ordering, idempotency, a retry), name the test that fails when it breaks. A loop over records read back proves nothing about records that vanished; assert the set is complete. When a finding proposes a fix, name each test, fixture, and doc that pins the behavior the fix would change, or say it changes none. A pin that contradicts the finding is evidence of the intended contract, and a finding that still stands must say why the pin is wrong; a snapshot regenerated from the code's own output is weaker evidence than a hand-written test. When a change can alter which tests run, trace which cases each affected job selects and whether setup failure, an empty selection, or an all-skipped suite can exit successfully.

Report concrete findings only. Each finding needs file:line, severity, and a specific failure scenario with inputs. A finding that proposes a fix also lists the existing tests, fixtures, and docs that fix changes, or says it changes none. After the findings, print the step 1 map. Say "No issues" only after the map is complete.

Only your final message is kept. Put every finding and the step 1 map in that one message, and do not refer to findings given earlier.
