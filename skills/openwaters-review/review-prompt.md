Code review, read-only. Do not modify files.

Review this branch as a change to a running system, not as a diff. Most real defects are in how the change meets code it does not touch. A review that only reads the diff has failed.

Step 1. Map the system before judging anything. For every table, column, file, cache, config key, env var, API field, message, and shared function the change reads or writes, search the whole repository for every other writer and reader: live ingest, replay, archive and historical loaders, converters, backfills, migrations, scheduled jobs, clients, scripts, and docs. List each one with file:line. Do not skip this step.

Step 2. Check the change's assumptions against every writer and reader from step 1, and against all the data that can actually exist: every source and prefix, rows written by other paths, rows written by older code before a migration, nulls, defaults, duplicates, and out-of-order or late data.

Step 3. Check the upgrade from what is deployed today: existing schema and data, migrations run in place, caches and their max-age, old clients still running, and rollback to the previous release. Is the in-place upgrade tested, or only a fresh install? For any marker or state only the new build writes, walk new build, rollback, older build runs, roll forward: does the marker still describe the data the older build left?

Step 4. Check every claim against the code: comments, READMEs, docs, policy, API descriptions, the commit messages (git log), and the PR description if one exists (given at the end of this prompt). Treat each claim, and each test or validation result, as a hypothesis to attack. Ask what cases the tests and validation data leave out. Follow the claims the change leans on but does not contain: when changed text cites another doc section, policy, or mechanism, confirm that mechanism exists in code. For every license, privacy, or redistribution condition attached to new data, such as an opt-out, suppression, attribution, or a ban on re-identification, find the code that enforces it on that data's path, or report that nothing does.

Step 5. Check the repository's own conventions and the checks it enforces in scripts and CI.

Step 6. Check these classes. Each asks you to name a concrete input, caller, or interleaving; a class that does not apply to the change needs no comment.

- Round trips. Data that is encoded and decoded again (paths built from keys, keys from names, serialization, URL or query encoding): is it reversible for every value that can exist, including separators, special characters, and empty values?
- List-valued fields. When code rewrites, parses, or validates a value that can hold several items (an HTML `srcset` or `sizes`, a comma-separated header, several `Link` values, a space-separated class or token list, a CSV cell), does it handle every item, or only the first or the whole string as one? Name the input with two or more items where a later one is left unchanged or misread.
- Every member of a kind. When the change or its description says something applies to every page, route, endpoint, command, or file of a kind ("every updates page", "all feeds"), list every member of that kind in the repository, including generated and dynamic routes, and check each one gets the change. Name the member that is left out.
- Changed conventions. When the change sets a new value for a precision, unit, rounding, threshold, limit, or format, search the whole repo for the old value written as a number, a multiplier (`* 1000`), a format call, or prose ("three decimals", "in seconds"). Name every other writer, comment, and doc that still applies or states the old value, including ones in packages the diff does not touch.
- Response shapes. When docs, a schema, or the change say a field is present in an answer, list every response that can carry that answer: other status codes, redirects, partial or truncated answers, other routes that share the handler or its lookup, and every other serializer of the same type. Does each emit the field, including its empty value (omitempty, nil versus empty collections, serializer settings that differ), or do the docs say which do not?
- Flag meanings. For each flag or status field the change sets, such as truncated, partial, or stale, find every code path that sets it, and check that its doc and description name all of them.
- Predicates. Does each query filter, guard, or condition enforce the exact rule its comment or doc states, at both bounds?
- Fallback chains. When a lookup tries candidates in order (a named item, then a default, then nothing), does a failure at any later stage of one candidate (its fetch, decode, validation, or timeout) move on to the next candidate, or end the whole chain? Name the candidate that is found but unusable and what the result falls back to.
- New parameters. When the change adds a parameter that changes a function's result (a kind, a mode, a locale), list every caller on the branch as it merges with the base, including callers the base added after the branch point, and check each passes it or has a stated reason not to.
- New input shapes. When the change makes code accept a second input shape (a fallback for a version, format, or value it used to assume), find every test, fixture, and caller that still derives its expectation from the old shape (a slice, a fixed pattern, a hardcoded format). Name the input where the code is right and the test or caller is wrong.
- Override combinations. When several settings, env vars, or flags can each override a default, check every mix of set and unset, not only all or none. Name the mix where an override collides with a value the code picks for another (two listeners on one port, two writers to one file), and rate it by its effect, not by how unlikely the mix seems.
- Refusals with other routes. When a rule refuses something (a validation fails, a permission is denied, a match is rejected), find every other rule, pass, or endpoint that can produce the same outcome for the same input (a later fallback, a second matching key, a bulk or admin path). Does each apply the same check? Name the input the first rule refuses and the other path that allows it anyway.
- Direction of conservative rules. When code or docs restate a conservative rule (fail closed, deny by default, round toward the safe side, never report more than was measured), read each test, filter, or rejection it implies literally and ask which side it keeps and which it drops. Name the input where following the wording removes the case the rule exists to protect.
- Precedence granularity. When one source, file, or record wins over another (supersede, precedence, dedupe, merge, "A wins over B"), what unit does the win apply to: a whole file, a record, or only the overlapping items? Name the partly overlapping input where whole-unit precedence discards data the winner does not hold.
- Torn snapshots. When state that must agree is saved or served together (two maps written to one file, a count and the list it counts), is it read under one hold of the lock or one transaction? Name the write that can land between two separately locked reads, and what the saved or restored result then gets wrong.
- Check-then-act on shared state. When code reads a shared object (a lock, a lease, a pointer, a marker file, a row) and then writes or deletes it based on what it read, can another writer change it in between? Name the interleaving, and check that the write is conditional on the version read (compare-and-swap, If-Match, a version column) rather than on a second read. Release and cleanup paths count too.
- Self-retriggering resets. When a condition on stored data clears a stamp, forces a resync, or triggers a rebuild, can the work it triggers legitimately end in that same state (an empty result, zero rows) so the reset fires again at every boot or run? Name the input that would loop it.
- Destructive syncs. When code removes stored state that its input no longer lists (prune, sync, mirror, cleanup), what happens when the input is empty, truncated, in a changed format, or holds entries the code cannot classify (an unknown key layout, a renamed file)? Name the input that removes existing data and still reports success, and check that the code stops the removal rather than only logging.
- Dangling references. When hand-maintained data (config, overrides, allow-lists, fixtures) refers to ids that another process generates, follow each consumer of that data through a later run where the target id is gone. Name the consumer that crashes or silently misbehaves, and the check that should report the stale reference instead.
- Removed code. What does it leave behind on systems that ran it (services, scheduled jobs, scripts, files and directories, env vars, secrets, storage, database objects, feature flags), and does the deploy clean it up?
- Long operations. For anything that can run for minutes or hours, check every timeout on its path: client and driver timeouts, proxy and load balancer limits, server execution limits, job runner and process supervisor timeouts.
- Resource use under a limit. When the change alters a query, algorithm, or data structure that runs under a memory, time, or size limit, do not stop at "unmeasured". You are read-only, so give the exact commands and production-like synthetic input that run the old and new code under the same limits and report peak memory and time, and name the input you expect to fail.
- Validation scale. Was the change validated only on small data, a mock, or a local stand-in for a production service, where production sizes or behavior take a different path (pagination, batching, multipart transfers, rate limits)?
- Other runtimes that load the code. When code is loaded by more than one runtime or environment (server and browser, Node and an edge worker, two language or platform versions), list the module-level code the change adds on that load path that depends on one of them: filesystem, process, globals, native modules, platform APIs. Name the environment where it fails at load, and whether any check actually starts that environment (a dry-run bundle does not).
- Secrets beside untrusted code. For each CI or deploy job that holds a secret (cloud keys, publish tokens, a write-scoped token), list every step that runs code from the branch or from dependencies (install scripts, a build, a test runner, a config file the tool loads). Name the step that could read or exfiltrate the secret, and check that building and publishing sit in separate jobs, with only built artifacts passed between them.
- Gate path lists. When a check decides "nothing relevant changed" from a list of paths (git diff -- paths, a CI paths filter), list every file that feeds what the check protects, including root manifests and lockfiles, build workflows, and container files. Name the file outside the list whose change slips past.
- Stated properties. For each property the change claims (concurrency, a limit, ordering, idempotency, a retry), is there a test that fails when the property is broken, not only one that passes when it holds?
- Per-record checks. When a test loops over records read back from an output (a dump, a restored file, an API listing) and checks each one, does it also assert the set is complete against what was written? A threshold or non-empty check passes when records are silently dropped, and the loop never sees them. Name the record that could vanish and still pass.
- Stale docs. Do specs, plans, design docs, or READMEs still describe what the change removes or replaces as current?
- Touch and keyboard reach. For anything shown only on hover (a tooltip, content revealed by :hover) or placed inside a link or button, can a phone user reach it with a tap, and a keyboard user with focus? A control nested in a link follows the link when tapped. Where the content is required (an attribution, a notice, an error), name what a touch or keyboard user loses.

Report concrete findings only. Each finding needs file:line, severity, and a specific failure scenario with inputs. After the findings, print the step 1 map. Say "No issues" only after the map is complete.
